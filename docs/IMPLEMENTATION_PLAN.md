# Пошаговый план реализации

План согласован с ограничениями VPS и проверкой GPC/PSP. Все задачи ниже пока открыты. Этапы выполняются последовательно; фактические версии зависимостей фиксируются при начале реализации.

## Этап 1. Каркас приложения

- [ ] Создать Go module, выбрать и закрепить версии Go, HTML-парсера и SQLite-драйвера.
- [ ] Разделить `cmd/handy-parser`, `internal/config`, `storage`, `extractor`, `runner`, `notify`, `web`.
- [ ] Реализовать команды `serve`, `check`, `migrate`, `healthcheck`.
- [ ] Добавить конфигурацию окружения, чтение секретов из файлов, проверки обязательных настроек.
- [ ] Реализовать структурированные логи без токенов, общий context и SIGTERM.

Готовность: приложение собирается для Linux amd64/arm64; ошибки конфигурации понятны; завершение прерывает сетевые запросы.

## Этап 2. Хранилище

- [ ] Миграции watches, state, history, runs, outbox.
- [ ] SQLite WAL, foreign_keys, busy_timeout и ограничения пула.
- [ ] CRUD наблюдений с валидацией и номером revision.
- [ ] Общая файловая блокировка выполнения проверок между контейнерами.
- [ ] Транзакционное сохранение изменения и события Telegram.
- [ ] Очистка устаревшей истории без удаления pending outbox.

Проверки: перезапуск сохраняет состояние; два процесса не выполняют серию одновременно; сбой транзакции не оставляет изменение без события; изменение настройки во время запроса не сохраняет устаревший результат.

## Этап 3. HTTP и универсальный CSS-парсер

- [ ] Один HTTP-клиент с повторным использованием соединений, таймаутами и пределом ответа после декомпрессии.
- [ ] Проверки URL/DNS/redirect и защита от доступа к внутренним адресам.
- [ ] CSS text/attribute, ровно одно совпадение, понятные ошибки.
- [ ] Нормализация цены и текста, денежное сравнение без float64.
- [ ] Профиль GPC и извлечение валюты.

Проверки на небольших фикстурах: дробная цена, пробелы, валюта, отсутствие/два совпадения, изменённая разметка, HTTP 429/5xx, timeout, слишком большой ответ, redirect на private IP, DNS rebinding. Использовать локальный тестовый HTTP-сервер с явно отделённой тестовой сетевой политикой.

Готовность: полученная по HTTP цена GPC совпадает с браузером; регулярные тесты не зависят от живого сайта.

## Этап 4. Обработчик PSP

- [ ] Разрешение исходной ссылки через urlResolver и проверка PRODUCT.
- [ ] Сохранение ID/SKU/названия, выбор действующей final_price.
- [ ] Валидация GraphQL errors, структуры, наличия и типа значения.
- [ ] Однократное повторное разрешение ссылки при устаревшем ID, контроль SKU.
- [ ] Предпросмотр результата в том же формате, что у HTML-парсера.

Проверки: товар со скидкой, без скидки, недоступный товар, ошибочный путь, другой SKU, HTTP 200 с GraphQL errors. Готовность: сохранённые примеры воспроизводимы; один ручной live smoke test сверяет цену с браузером.

## Этап 5. Проверки и Telegram

- [ ] Последовательный runner с общим бюджетом 4 минуты и небольшими паузами.
- [ ] Первый результат как baseline, история изменения, правила алертов.
- [ ] Счётчик ошибок, один алерт после трёх ошибок и сообщение о восстановлении.
- [ ] Outbox: ограниченные повторы, 429 retry_after, перенос оставшихся сообщений на следующий запуск.
- [ ] Экранирование названий/значений и лимит длины Telegram-сообщения.
- [ ] Отдельный статус ошибки доставки; стабильный ID события; отсутствие токена в ошибках.

Проверки: неизменная цена не уведомляет; ошибка источника не становится новой ценой; падение после сохранения не теряет событие; timeout Telegram оставляет событие pending; повторный запуск не создаёт событие изменения заново. Реальную отправку проверить в чате владельца после настройки токена.

## Этап 6. Веб-панель

- [ ] Авторизация, сессия, CSRF, rate limit входа.
- [ ] Список наблюдений со статусами и временем последней успешной проверки.
- [ ] Форма URL/метод/CSS/атрибут/тип/правило; PSP требует только URL и правила.
- [ ] Кнопка предпросмотра до сохранения; вывод исходного и нормализованного значения.
- [ ] Пауза, редактирование, удаление с подтверждением, история.
- [ ] Ручная проверка с немедленным ответом «запущено» и статусом выполнения; без дублирующих серий.
- [ ] Состояние Telegram и pending outbox, кнопка тестового сообщения, часовой пояс времени в интерфейсе.

Готовность: оба предоставленных товара добавляются через панель; проверены пустые формы, ошибки, узкий экран, вход/выход и ручной запуск одновременно с таймером. Сервер не исполняет произвольный HTML источника.

## Этап 7. Docker и эксплуатация

- [ ] Создать multi-stage Dockerfile с фиксированным toolchain, non-root runtime, CA certificates и timezone data при необходимости.
- [ ] Реализовать healthcheck и graceful shutdown; перенести проверенные примеры в рабочие deploy-файлы.
- [ ] Проверить права volume и secret-файлов для UID 10001.
- [ ] Проверить Compose: web + одноразовый check, ограничения памяти/CPU/PID, ротация логов.
- [ ] Протестировать systemd timer на Debian 13, ручной запуск, reboot, Persistent=true.
- [ ] Проверить timeout: контейнер check не остаётся висеть; следующий запуск возможен.
- [ ] Проверить резервную копию, восстановление и миграцию со старой схемы.

Готовность: установка выполняется по инструкции на чистом Debian 13; на VPS не требуется Go/Node; после проверки нет работающего контейнера check; веб-панель доступна только через предусмотренный способ доступа.

## Этап 8. Измерения на VPS

- [ ] Зафиксировать RAM/CPU до установки, отдельно накладные расходы Docker при его первом появлении.
- [ ] Измерить простой web, предпросмотр, ручную проверку и scheduled check на 10 страницах.
- [ ] Проверить лимиты 96 МиБ web / 192 МиБ check; ручная проверка обязана укладываться в лимит web.
- [ ] Замерить длительность, размер БД и поведение при недоступности обоих сайтов.
- [ ] Проверить доступность GPC/PSP с IP VPS без изменения политики других приложений.
- [ ] Провести сутки наблюдений: четыре срабатывания и отсутствие ненужных уведомлений.

Готовность: есть отчёт с измерениями, версиями и условиями. Если цели памяти не достигнуты, оптимизировать или согласовать новые лимиты до релиза.

## Этап 9. Первый релиз

- [ ] CI: format, vet, unit/integration tests, сборка обоих Linux-таргетов, Compose validation.
- [ ] На pull request проверять сборку образа без публикации.
- [ ] По тегу v0.1.0 опубликовать образ в GHCR, закрепив версии/commit SHA действий CI.
- [ ] Проверить публичное скачивание образа и установку по release Compose.
- [ ] Выпустить release notes, контрольные суммы deploy-архива и инструкции миграции.
- [ ] Убрать статус «проектирование» только после фактического прохождения критериев.

## Итоговая приёмка

Пользователь устанавливает образ через Docker, добавляет GPC и PSP, видит верные значения, получает сообщение о контролируемом изменении, после перезапуска сохраняет историю. Проверки выполняются четыре раза в день; ошибки не вызывают ложных ценовых алертов; между проверками парсер не работает; восстановление из резервной копии проверено.
